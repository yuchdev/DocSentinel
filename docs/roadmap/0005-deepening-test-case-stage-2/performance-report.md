# Fast-profile performance report (Story 15.0 Task 02)

This report compares fast-profile startup and runtime **before** Milestone 0005
(commit `e05509a`, three fast rules `DS101`/`DS102`/`DS103`, no shared scanner) against
the **current** tree (sixteen fast rules `DS101`-`DS118` built on the shared
`markdown_blocks.py` scanner). It follows Story 15.0 Task 02's rule: there is no
universal sub-second guarantee; the goal is to report honestly and flag regressions
greater than 2x. All measurements were taken on an otherwise-idle machine.

## Machine and toolchain

| Item | Value |
| --- | --- |
| OS | Darwin 21.6.0 (x86_64) |
| CPU | Intel Core i7-5650U @ 2.20 GHz |
| Python | 3.12.13 |
| uv | 0.11.6 |

## Method

- Corpus generated by `scripts/bench_corpus.py` (deterministic, standard-library only):
  500 and 2000 Markdown documents, each mixing headings, inline and reference-style
  links, an image, a reference definition, a fenced code block and a GFM table.
- Scan wall-clock: five subprocess runs of `docsentinel scan <corpus> --format json`,
  median reported. Each subprocess pays the one-time `import docsentinel` cost, so the
  medians below are end-to-end CLI latency.
- Import cost: `python -X importtime -c "import docsentinel"`, cumulative microseconds
  for the top-level `docsentinel` import.
- Before/after share one interpreter and one installed dependency set; the "before"
  code is loaded from a `git worktree` of `e05509a` via `PYTHONPATH`, verified to import
  from that worktree and to register exactly `DS101`/`DS102`/`DS103`.

## Import cost (startup)

| Build | `import docsentinel` cumulative | spaCy imported |
| --- | --- | --- |
| Before (`e05509a`) | 909.5 ms | yes |
| After (current) | 83.2 ms | no |

The after build is about **10.9x faster to import**. Task 02 B made the deep analyzer's
spaCy/textacy dependency lazy, so a plain `import docsentinel` (and every fast or standard
run) no longer pays spaCy's ~0.8 s load. This is a clear improvement, not a regression.

## Scan wall-clock (end-to-end CLI)

| Corpus | Before median | After median | Ratio (after / before) |
| --- | --- | --- | --- |
| 500 files | 1.415 s | 3.241 s | 2.29x |
| 2000 files | 2.514 s | 13.451 s | 5.35x |

Because each subprocess includes the one-time import, the approximate scan-only work
(median minus the import cost above) is:

| Corpus | Before scan-only | After scan-only |
| --- | --- | --- |
| 500 files | about 0.51 s | about 3.16 s |
| 2000 files | about 1.60 s | about 13.37 s |

**Flagged: the fast scan runtime regresses well beyond 2x** (5.35x end-to-end, and about
8x on scan-only work at 2000 files). This is expected in direction - the tree grew from 3
to 16 fast rules - but the magnitude is worth recording. The after build scales roughly
linearly in document count (3.24 s to 13.45 s is about 4.15x for 4x the files), so the
regression is a larger constant per document, not a super-linear blow-up.

## Analysis and recommendation

The cost is spread fairly evenly across the eight scanner-backed rules
(`DS104`/`DS105`/`DS106`/`DS108`/`DS109`/`DS116`/`DS117`, plus `DS101`): each one calls the
shared `markdown_blocks` scanner independently, so the corpus is tokenised roughly eight
times per run with no shared or cached parse. `DS113` adds a filesystem `stat` per
asset reference on top. No single rule is pathological and the per-document cost is linear;
the regression is the sum of many independent re-parses.

The natural optimisation - already noted in `status.md` carry-forwards (unify the two
table parsers, a headings-only fast path, a shared per-document parse cache) - is a
cross-rule refactor that should be designed under its own ADR, not bolted on in this task.
It is recorded here as the top fast-profile performance follow-up.

No automated performance assertion is added from these numbers: the adversarial runtime
suite (`tests/integration/test_adversarial_runtime_cases.py`) asserts only a generous
120 s ceiling and determinism, never a tight wall-clock bound, so it cannot flake on a
loaded machine.
